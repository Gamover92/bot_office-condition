# Дизайн: HTML-виджеты Telegram в /climate

Дата: 2026-11-10. Статус: на согласовании.

## Зачем

Сейчас `/climate` — это PNG-график (matplotlib) плюс inline-клавиатура
(датчик / метрика / период / обновить). Каждое переключение — это round-trip к
серверу и перегенерация картинки. Telegram выпустил HTML-виджеты
([widget-sandbox](https://github.com/TelegramMessenger/widget-sandbox),
[Bot API 10.4, 9 ноября 2026](https://core.telegram.org/bots/api-changelog)):
мини-HTML прямо в пузыре сообщения, с тапами, темой клиента и состоянием,
которое бот может обновлять. Цель — заменить связку «PNG + кнопки» на один
интерактивный график: переключение метрики и периода происходит мгновенно внутри
виджета, а текущие значения обновляются сами, без новых сообщений.

## Цели

- Виджет `/climate`: график на canvas с зонами 🟢🟡🔴 (как в PNG), переключение
  метрики и периода тапами внутри виджета, без обращений к серверу.
- Живые последние значения: цифры в виджете обновляются сами, без новых
  сообщений (бот правит `public_data` через `editMessageWidgetData`).
- Текстовая сводка остаётся в caption — она же fallback для старых клиентов.
- Личные чаты получают виджет; группы продолжают получать PNG, пока Telegram
  не откроет виджеты в группах (серверный конфиг, дата неизвестна). Включение
  в группах — одним флагом конфигурации.
- Спайком (фаза 1) проверить весь путь end-to-end до постройки полной версии.

## Не-цели

- Уличная погода и AQI: датчик их по MQTT не отдаёт (проверено по живому
  payload и документации), внешние API не добавляем — проект остаётся локальным.
- Запросы из виджета к боту (`widget_query`, `allow_queries`): не нужны в
  выбранной модели, данные запекаются. Это также снимает проблему с тем, что
  aiogram 3.31 не знает новый тип апдейта.
- Виджеты в утреннем отчёте и алертах: отчёт уходит в группы, где виджеты
  сейчас запрещены. Пересматриваем, когда Telegram откроет группы.
- Инлайн-режим и пересылка: в проде запрещены сервером.

## Анти-цели (что считаем провалом, даже если технически работает)

- Виджет хуже читается, чем PNG, на телефоне (ширина пузыря ~362 px).
- Регрессия группового сценария: в группе всё должно работать ровно как сейчас.
- Рост нагрузки: правки `public_data` чаще одного раза в несколько секунд.

## Ограничения (подтверждено документацией и changelog)

- HTML виджета: ≤ 32 KB исходника, ≤ 4 KB после `zlib.compress(html, 9)`.
  Никаких внешних ресурсов и сети; только inline CSS/JS, `data:`-картинки.
- **HTML неизменен после отправки.** Меняется только состояние:
  `public_data` и `chat_data`, каждое ≤ 1024 байта текста, пишет только бот.
- Статичный (не shared) виджет хранит `public_data` в самом сообщении; бот
  правит его через `editMessageWidgetData` по координатам сообщения, правки
  доезжают до клиентов лёгким апдейтом и идут через обычный флуд-контроль
  `sendMessage`. Shared-объекты (`is_shared`, `widget_id`) не используем:
  их HTML тоже неизменен, поэтому переиспользование объекта означало бы
  вечно устаревший график; а единственное их преимущество — единое состояние
  у пересланных копий — в проде бесполезно, т.к. пересылка запрещена.
- Прод-ограничение Bot API 10.4: виджеты **только в личных чатах с ботом**,
  автоматический protected content (не пересылаются), в группах —
  `INPUT_MEDIA_WIDGET_NOT_ALLOWED`, inline закрыт.
- Старые клиенты (< layer 233) видят `messageMediaUnsupported` + caption:
  текста сводки достаёт, графика не будет. Принято.
- aiogram 3.31 поддерживает Bot API 10.3: типов и методов виджетов нет.
  Исходящие вызовы (`sendWidget`, `editMessageWidgetData`) делаем сырым
  HTTP тем же токеном (через `bot.session` или aiohttp). Входящие апдейты
  виджетов не нужны (запросов нет, `allow_queries` не ставим).
- Размер пузыря: ширина 430 px десктоп / ~362 px мобила, высота до 600 px;
  вёрстка в процентах, `vh`/`vmin` не работают.
- JS в песочнице: без единого блока > 500 мс, без постоянной анимации
  (CPU-квота); тема приходит через `TelegramWidget` (тёмная/светлая).

## Подходы (рассмотрены)

1. **Всё запечено в HTML.** Все метрики × периоды одного датчика запекаются
   при отправке; переключение локальное. Просто, работает в копиях, но данные
   — снимок на момент отправки.
2. **Запросы к боту (`widget_query`).** В HTML только дефолтный вид, остальное
   догружается по тапу (ответ ≤ 1024 байт). Свежие данные, но лимиты
   (5 запросов / 5 с), ответ видит только тапнувший, и aiogram не умеет
   принимать новый тип апдейта — нужен отдельный приёмник.
3. **Гибрид (выбран).** Серии запечены для локального переключения, а свежие
   последние значения приезжают через `public_data`, которое бот правит в
   сообщении (`editMessageWidgetData`). Живой эффект без входящих апдейтов,
   без лимитов запросов и без shared-объектов.

По стратегии внедрения рассматривали: строить сразу с фолбэком (выбрано),
только спайк, ждать открытия групп. Идём полным пайплайном, фаза 1 — спайк.

## Как строим (решённая часть)

### Фаза 1 — спайк (throwaway, без тестов)

Минимальный статичный виджет в личке: текущие значения + один спарклайн CO₂
за 24 ч. Цели спайка:

- пройти отправку `sendWidget` сырым HTTP из нашего кода;
- измерить реальный сжатый размер и понять бюджет данных (сколько точек и
  метрик реально влезает в 4 KB с запасом ~3800 B);
- посмотреть рендер на десктопе и телефоне, тёмную/светлую тему;
- проверить `editMessageWidgetData` и обновление цифр из `public_data`.

Спайк не идёт в продакшен-код; выводы фиксируем и возвращаемся к дизайну,
если бюджет данных меняет расклад (например, придётся резать периоды или
метрики).

### Фаза 2 — полная версия

- **Новый модуль** (например `app/widget.py`): сборка HTML из шаблона + данных,
  контроль размера (`zlib.compress(html, 9)` ≤ ~3800 B), отправка и правки
  состояния сырым HTTP. Код спайка — основа, но переписывается начисто.
- **Статичный виджет на сообщение**: каждый `/climate` шлёт новый виджет со
  свежими сериями, запечёнными в HTML, и с `public_data` (компактный JSON
  последних значений, ≤ 1024 B с запасом). Бот запоминает координаты
  отправленных виджет-сообщений (chat_id + message_id, в SQLite) и при новых
  MQTT-данных правит `public_data` свежих сообщений (троттлинг: не чаще раза
  в несколько секунд на сообщение; обновляем только сообщения моложе
  N часов — старые цифры замирают, это приемлемо). `chat_data` не используем;
  выбор метрики/периода не запоминается, как и сейчас.
- **«Обновить»**: цифры живые без кнопки; кнопка «🔄 Обновить» в клавиатуре
  под виджетом шлёт новое виджет-сообщение со свежим графиком и удаляет старое
  (тот же паттерн пересоздания, что в `edit_view`).
- **Данные в HTML**: при отправке `/climate` бот запекает серии всех
  отображаемых метрик × периодов (6 ч / 24 ч / 7 д) одного датчика с
  прореживанием под бюджет; формат кодирования — компактный (решение
  строителя, по итогам спайка). Времена — epoch + часовой пояс офиса
  (`settings.tz`) запечён в HTML: подписи осей совпадают с PNG, а не с
  поясом зрителя (бот офисный, смотрят его в контексте офиса).
  Переключение датчика остаётся снаружи: виджет одного сообщения про один
  датчик; если датчиков несколько, клавиатура под сообщением — только для
  переключения датчика и обновления (правкой `chat_data` это не выразить —
  серия в 1024 B не влезает).
- **Маршрутизация по типу чата**: личка → виджет; группа → текущий путь PNG
  без изменений. **Любая** ошибка отправки виджета (в т.ч.
  `INPUT_MEDIA_WIDGET_NOT_ALLOWED`, переполнение размера, сбой API) →
  фолбэк на PNG-путь, пользователь всегда получает рабочую сводку.
  Флаги конфигурации: `WIDGETS_ENABLED` (мастер-выключатель, по умолчанию
  вкл.) и `WIDGETS_IN_GROUPS` (по умолчанию выкл.; включаем, когда Telegram
  откроет группы).
- **Caption** — та же текстовая сводка, что сейчас (`summary.caption`),
  без изменений логики.
- **Owner-lock кнопок**: поведение «кнопки только вызвавшего» сохраняется для
  оставшейся клавиатуры (переключение датчика).

## Что оставлено строителю

- Вёрстка и отрисовка виджета (canvas vs SVG, раскладка под 362–430 px).
- Формат запечённых данных и прореживание (по измеренному бюджету спайка).
- Структура JSON в `public_data`, интервал троттлинга правок и возраст N,
  после которого сообщение перестаёт получать обновления.
- Как именно делать сырые вызовы Bot API рядом с aiogram (свой мини-клиент
  на aiohttp или кастомный метод aiogram).
- Схема SQLite для координат виджет-сообщений и её очистка.
- Тесты: юнит-тесты сборки HTML/кодирования/контроля размера; рендер —
  руками через dev app песочницы (`pnpm dev`) и живой Telegram.
- Обновление README и `.env.example` под новые флаги.

## Открытые риски

- Telegram может открыть группы с дополнительными ограничениями — флаг
  `WIDGETS_IN_GROUPS` позволит проверить без переделки.
- 4 KB может не хватить на 8 метрик × 3 периода — решится по итогам спайка
  (меньше точек, меньше периодов внутри виджета, или период «7 д» только
  снаружи).
- `editMessageWidgetData` для статичных виджетов идёт через флуд-контроль
  `sendMessage`: при частых обновлениях MQTT и многих живых сообщениях
  троттлинг должен быть суммарным, не только по сообщению.
